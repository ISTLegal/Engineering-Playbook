# Branch Naming Convention

A comprehensive guide for creating consistent, descriptive, and meaningful branch names that improve code organization and team collaboration.

## 🎯 Purpose

Proper branch naming is crucial for:

- **Code Organization**: Easy identification of branch purpose and scope
- **Team Collaboration**: Clear communication about what each branch contains
- **Issue Tracking**: Direct connection between branches and project issues
- **Automation**: Enables automated workflows and CI/CD processes
- **Code Review**: Helps reviewers understand the context quickly

## 📋 Branch Naming Format

### Standard Format

```
{type}-{description}-{issue-id}
```

### Components Breakdown

| Component     | Description                  | Examples                                   |
| ------------- | ---------------------------- | ------------------------------------------ |
| `type`        | Branch type (required)       | `feat`, `fix`, `chore`, `docs`, `refactor` |
| `description` | Brief description (required) | `user-authentication`, `login-validation`  |
| `issue-id`    | Related issue ID (optional)  | `123`, `PROJ-456`, `#789`                  |

## 🏷️ Branch Types

### Primary Types

| Type       | Description       | Use Case                           | Example                         |
| ---------- | ----------------- | ---------------------------------- | ------------------------------- |
| `feat`     | New features      | Adding new functionality           | `feat-user-dashboard-123`       |
| `fix`      | Bug fixes         | Resolving issues                   | `fix-login-error-456`           |
| `chore`    | Maintenance tasks | Dependencies, configs              | `chore-update-dependencies-789` |
| `docs`     | Documentation     | README, guides, comments           | `docs-api-documentation-101`    |
| `refactor` | Code improvements | Restructuring without new features | `refactor-database-queries-202` |

### Secondary Types

| Type    | Description              | Use Case              | Example                          |
| ------- | ------------------------ | --------------------- | -------------------------------- |
| `perf`  | Performance improvements | Optimizing code       | `perf-database-indexing-303`     |
| `test`  | Testing related          | Adding/updating tests | `test-user-service-coverage-404` |
| `style` | Code style changes       | Formatting, linting   | `style-eslint-configuration-505` |
| `ci`    | CI/CD changes            | Build, deployment     | `ci-github-actions-setup-606`    |
| `build` | Build system changes     | Webpack, bundlers     | `build-webpack-optimization-707` |

## 📝 Naming Rules

### Description Guidelines

1. **Use kebab-case**: All lowercase with hyphens

   ```bash
   ✅ feat-user-authentication
   ❌ feat_user_authentication
   ❌ featUserAuthentication
   ```

2. **Be descriptive but concise**: 2-4 words maximum

   ```bash
   ✅ feat-user-dashboard
   ✅ fix-login-validation
   ❌ feat-add-new-feature-for-user-dashboard
   ```

3. **Use present tense**: Describe what the branch does

   ```bash
   ✅ feat-add-user-authentication
   ❌ feat-added-user-authentication
   ```

4. **Avoid special characters**: No spaces, underscores, or special symbols
   ```bash
   ✅ feat-user-management
   ❌ feat user management
   ❌ feat_user_management
   ```

### Issue ID Guidelines

1. **Include issue number**: Link to project management system

   ```bash
   feat-user-authentication-123
   fix-login-error-456
   ```

2. **Use consistent format**: Match your project's issue numbering

   ```bash
   # GitHub Issues
   feat-user-dashboard-123

   # Jira Tickets
   feat-user-dashboard-PROJ-123

   # Linear Issues
   feat-user-dashboard-LIN-123
   ```

3. **Optional for small changes**: Not required for minor fixes
   ```bash
   chore-update-readme
   style-fix-formatting
   ```

## 🔄 Branch Lifecycle

### Creation

```bash
# Create and switch to new branch
git checkout -b feat-user-authentication-123

# Or using newer syntax
git switch -c feat-user-authentication-123
```

### Naming During Development

```bash
# If scope changes, consider renaming
git branch -m feat-user-authentication-123 feat-user-auth-system-123

# Update remote branch name
git push origin -u feat-user-auth-system-123
git push origin --delete feat-user-authentication-123
```

### Cleanup

```bash
# Delete local branch after merge
git branch -d feat-user-authentication-123

# Delete remote branch
git push origin --delete feat-user-authentication-123
```

## 🛠️ Automation Integration

### CI/CD Integration

Branch names can trigger different workflows:

```yaml
# GitHub Actions example
name: CI/CD Pipeline
on:
  push:
    branches:
      - "feat/*"
      - "fix/*"
      - "chore/*"
  pull_request:
    branches:
      - "feat/*"
      - "fix/*"
      - "chore/*"
```

### Automated Checks

```bash
# Pre-commit hook to validate branch names
#!/bin/bash
branch_name=$(git rev-parse --abbrev-ref HEAD)

if [[ ! $branch_name =~ ^(feat|fix|chore|docs|refactor|perf|test|style|ci|build)-[a-z0-9-]+(-[0-9]+)?$ ]]; then
    echo "❌ Invalid branch name: $branch_name"
    echo "✅ Use format: {type}-{description}-{issue-id}"
    echo "✅ Examples: feat-user-auth-123, fix-login-bug-456"
    exit 1
fi

echo "✅ Valid branch name: $branch_name"
```

## 📊 Branch Naming Best Practices

### Do's ✅

- **Be Consistent**: Follow the same pattern across all branches
- **Be Descriptive**: Clearly indicate what the branch contains
- **Include Issue ID**: Link to project management when possible
- **Use Present Tense**: Describe what the branch does
- **Keep It Short**: 2-4 words for description
- **Use kebab-case**: All lowercase with hyphens

### Don'ts ❌

- **Don't Use Spaces**: Use hyphens instead
- **Don't Use Underscores**: Use hyphens for consistency
- **Don't Be Vague**: Avoid generic terms like "update" or "fix"
- **Don't Use Special Characters**: Stick to alphanumeric and hyphens
- **Don't Make It Too Long**: Keep descriptions concise
- **Don't Skip the Type**: Always include the branch type

## 🔍 Branch Naming Patterns

### Pattern Examples

```bash
# Feature Development
feat-{component}-{action}-{issue-id}
feat-user-registration-123
feat-payment-processing-124

# Bug Fixes
fix-{component}-{issue}-{issue-id}
fix-login-validation-201
fix-database-connection-202

# Maintenance
chore-{category}-{action}-{issue-id}
chore-dependencies-update-301
chore-configuration-setup-302

# Documentation
docs-{section}-{action}-{issue-id}
docs-api-endpoints-401
docs-deployment-guide-402
```

### Advanced Patterns

```bash
# Multi-component features
feat-auth-and-user-management-123
feat-dashboard-and-analytics-124

# Environment-specific
feat-staging-deployment-config-125
feat-production-monitoring-setup-126

# Version-specific
feat-v2-api-migration-127
feat-legacy-support-removal-128
```

## 🚀 Migration Strategy

### Updating Existing Branches

If you have existing branches with different naming conventions:

```bash
# Rename local branch
git branch -m old-branch-name feat-new-description-123

# Update remote branch
git push origin -u feat-new-description-123
git push origin --delete old-branch-name
```

### Team Adoption

1. **Document the Standard**: Share this guide with the team
2. **Update CI/CD**: Configure automated checks
3. **Gradual Migration**: Update branches as they're worked on
4. **Team Training**: Conduct sessions on the new standard
5. **Monitor Compliance**: Regular reviews and feedback
